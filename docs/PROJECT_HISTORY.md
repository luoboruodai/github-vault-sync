# GitHub Vault Sync｜开发历程与后续接手指南（公开脱敏版）

> **首发日期：2026-10-08；公开版本：v0.1.0。** 本文件为后续开发者准备，按时间线整理需求对话、实际实施、反复发现的缺陷、安全边界与测试。它是**结构化的脱敏会话纪要，不是逐字导出的聊天记录**：公开仓库不收录笔记正文、个人截图、具体本机 Vault 路径、GitHub 身份、访问令牌或恢复密钥。原始对话应仅在私有的 Codex 任务中回看。不要将个人 Vault 或本机 `data.json` 添入此公开仓库。

## 0. 仓库定位与版本说明

- **此公开仓库**：插件源码、测试、英文/中文 README、公开开发记录，以及 `releases/v0.1.0/` 中可下载的无凭据安装包。
- **用户自己的私有仓库**：Obsidian Vault 的 Markdown、附件及加密配置。插件强制要求此笔记数据仓库为私有；绝不应把笔记或凭据放进公开插件项目仓库。
- 项目先以内部原型版本号 `0.1.x → 0.2.x → 0.3.x → 0.4.0` 迭代；应用户要求，以现有功能基线重新编号为**第一个公开发行版 v0.1.0**。发布资产 `manifest.json`、`package.json`、`versions.json`、Tag 和 ZIP 都应一致。内部已安装的 `0.4.0` 与公开首版 `0.1.0` 的编号并非“升级”关系，不能依赖 Obsidian 按版本号自动覆盖；不要为了首版发布无故替换正在工作的 Vault 插件。

### 同步主链路

1. 手动点击「预览并同步」：先获取远端分支并扫描本地；验证路径、敏感文件、Git/LFS 环境与密文状态，按 Markdown → 笔记附件 → Obsidian 配置 → 其他文件展示变化。预览阶段**不创建提交、不上传**。
2. 预览保存远端提交 SHA 与本地内容指纹；必须由人选择**同一篇 Markdown 冲突**的本机/仓库/逐项优先方式。查看单篇笔记内容是只读操作。
3. 真正暂存前重新抓取远端 SHA、检查本地内容指纹；若其中任何一端改变，拒绝过期预览。只暂存经过 Vault 扫描允许的文件，并核对现存文件确已进入 Git 索引；已删除文件按预期从索引移除。
4. 如发生分叉，把各自独立的改动合并；同一路径 Markdown 冲突按这次的人工选择处理，并把未选中的版本放在本地冲突目录。配置、加密包、附件不因 Markdown 优先方而自动覆盖。没有 force-push。
5. Git LFS 的实际传输计数由 Git 输出驱动；Git 没有给出百分比时界面保持不确定进度，成功才标 100%。
6. 即时模式仅在本地事件防抖后/固定间隔检查变化并提醒，不调用自动上传路径；远端插件可执行代码或加密包变动也只能人工处理。

### 差异并不是“自动判定最新”

差异百分比 = 两端不相同的文件路径数量 ÷ 两端文件路径并集。它不是文字内容相似度。设备时钟、文件 mtime 或提交时间都不能单独证明哪篇文章**语义上最新**；用户需在并排预览中判断。丢失方的 Markdown 字节副本会备份，Git 提交历史仍可追溯。

## 3. 安全边界与密钥恢复

- **代码仓库公开，笔记仓库必须私有。** 项目发布资产不含 `data.json`、PAT、恢复密钥或 Vault 正文。
- `data.json`、常见凭据点文件、Vault `.git`、冲突备份目录一律禁止明文暂存；允许的插件 `main.js`/CSS 等做高置信度令牌扫描，扫描结果并非形式化安全证明。GitHub PAT 保存在本机插件配置（权限尽可能限制为当前用户），不进入 Git remote URL。
- AES-256-GCM 使用随机 nonce、认证标签及 AAD；客户端把插件 `data.json` 和指定例外目录（含独立嵌套 `.git`）封入单个密文文件。随机 256 位恢复密钥保存在 Vault 之外，仅由用户自己保管；加密包里的文件名和内容经加密。解密会验证标签/HMAC、限制总大小及路径，先备份现有本地文件，再由用户手动恢复。默认不覆盖本机插件的 GitHub 登录。
- 自动合并配置/执行脚本可能覆盖凭据或自动运行来自远端的代码，因此加密包与远端可执行插件文件更新需人工审核。明文例外目录依然排除；密文副本不是 GitHub 公共项目的资产。
- 如果用户丢失恢复密钥，云端加密配置无法解密；应将恢复密钥单独、安全地备份，不要在截图、聊天、Vault 或公开仓库传播。
- 本项目先前在**私有笔记仓库**发现并从当前树移除一份仅含普通开发设置的点配置文件。Git 历史不会因从当前树删除而自动清除；这也是发布公共项目时从第一次提交就必须脱敏的原因。此公开新仓库从零建立，不应携带私有笔记仓库的历史。

## 4. 开发过程中发现过的具体问题与修复

1. **glob 与 Git LFS 范围不一致**：如 `*.png` 应匹配子目录附件；扫描与 Git 属性需同一套语义。修改后加入中英文路径、Windows 不兼容名与大小写冲突测试。
2. **仅写 `.git/info/exclude` 不足以保护曾经追踪过的凭据**：旧文件仍可能被 `git add --all` 提交。改为逐个暂存扫描允许的路径，遇到已追踪而现被排除的文件则阻止提交；加入文件级敏感内容及真实 Git 暂存测试。
3. **排除规则切换留下陈旧 ignore**：最初开关 `.obsidian` 或删除插件目录排除规则后，本机 `.git/info/exclude` 仍保留旧模式，Git 不能暂存新允许文件。改用带管理标记的 exclude 区段和旧配置迁移，并保存用户自写规则。
4. **LFS 安装次序和钩子**：`git lfs env` 并不能保证新仓库已装 pre-push 钩子；必须先 Git init，再本地 `git lfs install --local`，否则可能仅上传 LFS 指针。长耗时大附件的 push 超时调大，进度没有可信计数时保持不确定。
5. **私有仓库为空时的断点重试**：首次 LFS push 若中断，后续 Upload 不应对不存在的 `origin/main` 直接 fetch。加入空分支重试测试。
6. **扫描误报与漏传**：第三方插件压缩 JS/CSS 里常出现 `password:` 或形如 `task-...` 的 CSS 类名，原规则误判；改为在代码资产中只拦高置信度的完整 Token/私钥或硬编码长值。包含 NUL 的插件 JS 仍可作为代码扫描。另一方面，某个已安装插件本身含嵌套 `.git`：外层 Git 会悄悄忽略其文件。现在扫描主动报错或要求排除，并在暂存后核对索引文件数。
7. **删除文件被误判“漏暂存”**：用户删除另一个同步插件时，索引里消失的 7 个文件是**正确的删除**，不能算漏传。修正索引核对只要求现存允许文件仍在索引，增加删除集成测试。
8. **加密包无变化却频繁重写**：Obsidian 保存 JSON 时可能改变字段顺序及状态日志。加密源先对 JSON 递归稳定排序，本插件的短暂状态/日志字段不入归档；添加重启前后稳定性测试。远端密文与本机明文同时变化时停止覆盖，要求手动处理。
9. **“及时同步”与每次确认冲突**：旧原型曾自动推送。用户要求每次上传前明确选择本机或仓库优先后，已将定时行为改成**只读检查 + 提醒**，绝不绕过确认。
10. **安全合并不同类型的文件**：方向偏好只自动作用于 Markdown 冲突；插件配置、加密包、二进制仍进入逐项冲突中心。笔记冲突同时保存未选文本版本以便恢复，不通过覆盖所有文件的方式实现所谓“最新”。

## 6. 已知边界与后续开发建议

- Git LFS 对象大小、额度、网络环境会影响初次上传；进度在无 Git/LFS 对象计数时无法准确报字节百分比。
- 冲突备份中的非 Markdown Git LFS 文件可能是 Git 指针，不等于已水合的完整附件；两端 Git 提交仍保留原对象，但下一版应在独立目录里水合并验证附件副本。
- 加密配置归档目前是一份整体密文；两台设备同时修改插件配置时，不能做 `data.json` 字段级自动合并，应继续要求人工判断或下一版改成逐文件加密镜像。
- 密钥导出为当前用户可读的本地文件；如果仅存在同一台磁盘，磁盘损坏后云端密文无法恢复。未来可设计更好的跨设备密钥迁移与可靠轮换，但不应将密钥同步到仓库。
- OAuth Device Flow 需要用户自己配置 GitHub OAuth App Client ID；包内没有通用开发者应用 ID。平台扩展到移动端尚未实现。
- 预览基于已保存的 Vault 文件、Git 状态及远端 SHA；未落盘的编辑器缓冲、设备时钟并不能保证“自动选到最新”。确认前仍应保存正在写的笔记。
- 设置页与弹窗做了主题变量、自适应布局和键盘可达性，实际视觉 QA 应在浅色/深色主题与较窄窗口、长路径、多冲突下继续人工检查；测试主要验证逻辑与构建，不等同于真实 Obsidian UI 端到端测试。
- 如果用户以后希望“无人确认的全自动上传”，必须重新设计独立的预授权边界、明文敏感内容审计、冲突策略和撤销机制；当前版本故意只自动检查。

## 7. 下一位开发者的优先检查步骤

1. 先读本文件、双语 README、[`src/types.ts`](../src/types.ts) 与核心引擎、测试；在本机测试 Vault 而非生产 Vault 操作。
2. 运行类型检查、全套临时 Git 仓库测试和生产构建，确认 `manifest` 与 Release ZIP 一致。
3. 不把任何真实 Token、恢复密钥、Obsidian `data.json`、用户原始对话截图或个人 Vault 数据写入公开代码仓库或 Release 资产。
4. 准备有用户授权且作用域受限的 GitHub 令牌发布新 Release；检查私有**笔记仓库**与公开**插件仓库**不要混淆。
5. 更改上传语义或恢复方式时，增加“先只读预览、后人工确认、丢失版本备份、远端变更拒绝过期授权”的集成测试，再部署。
